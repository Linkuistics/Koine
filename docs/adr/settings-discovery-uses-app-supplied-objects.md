# Settings discovery uses app-supplied objects

Modern System Settings discovery uses the installed application's scripting
objects and explicit pane/anchor reveal command. Ordinary reads address a
validated already-running target with exact no-prompt events. Background
preparation and selected reveal are separate capability-authorized effects.
Conditional Automation setup belongs only to an explicit human action in Koine's
local explaining UI, through a private local-console seam; GraphQL and bearer
management authority cannot initiate it. The [native discovery spec](../specs/workspace-search.md#system-settings-read-and-exact-target)
defines their contracts. Try unchanged signing posture first and introduce
only the entitlement/usage description needed if useful exact events require
explicit authorization.

Exact-event preflight is a qualification check, not an event-scoped OS grant.
Automation consent covers the Koine-host/System Settings target pair: allowing
one request can affect other events to that same target. The UI discloses this
reach, retains a pending request after its wait expires and offers manual
Privacy & Security → Automation guidance after denial. Read, preparation and
reveal never request consent or replay a late request. This preserves Machine's
UI-owned consent boundary while accepting the additional local UI and late-answer
ownership work. A client-triggered setup mutation would let transferred bearer
authority present OS consent without Koine's explanation and is not admitted.

The [shipped dictionary and SDK analysis](../verification/native-discovery-sources.md#shipped-scripting-interface)
provides named objects rather than guessed extension IDs/deep links. This
accepts runtime-source/target and conditional consent costs, without claiming
that any event needs consent or exposes all ordinary areas correctly. Missing
required areas remain unmet work. Two full ID-associated properties/anchor sweeps detect
observed changes without certifying lazy completeness; positive choices remain
PARTIAL/UNKNOWN and empty anchors null. Cold preparation is process-only.
Independent finite cold/warm qualification must preserve all exposed choices;
missing anchors cannot be excused by stable IDs or hidden extension-loading reads.
Confirmation timeout retains uncontradicted complete-first-map positives as
PARTIAL/TIME_LIMIT/UNKNOWN rather than discarding them for redundant change
detection. Earlier incomplete-sweep timeout and count/call/copy overflow remain
FAILED/null. Lazy no-such-object also cannot establish selected destination
absence: failed exact re-resolution starts no reveal/activation. A separate
unvisited-incarnation reveal must qualify a known earlier pane/anchor; honest
uncertainty cannot excuse an unusable ordinary destination.
Private sidebar parsing has unsupported format
and conditional-visibility costs; two documented URLs alone would reduce the
agreed useful category. Reopen that choice only if actual exact-event qualification
cannot deliver useful prompt-free reads or a required destination, with a concrete
consumer consequence and explicit alternative. Client-owned raw search remains
[the ownership decision](raw-filesystem-search-belongs-to-clients.md).
