## Findings

### P1 — The region replay has no place in the two-temporary choreography (medium-high)

What the spec now requires:

- k122 adds a region replay. A successful reported path is validated by one
  no-follow walk that observes the region witness. The rule is to "close the
  prior A/B pair, then use A/B for replay", and a "closed-candidate replay still
  has the stated ABA limit" (spec:533-548).
- Final admission must precede bundle inspection (spec:303-304, 307-309).

What k119's choreography still says, unchanged in structure:

- Canonical **and** native metadata checks run "at the final pair" of held
  descriptors (spec:1664).
- `resourceValues` must be bracketed by directory identity and canonical checks
  (spec:1503).
- The candidate is reacquired and A/B are held "through the commit/discard
  decision" (spec:1667). The finalized name and path come from the latest report
  (spec:573-574), which is taken in that last phase.

No phase row shows a replay step, and neither do `search-inspection.d2` or
`search-canonical.d2`.

- **Counterexample.** A checked `/Applications/Tool.app` link resolves to a
  bundle. Region admission must come before Bundle or `resourceValues`. The
  replay needs A/B closed, but the metadata bracket needs the candidate held.
  Every way through breaks a stated rule:
  - metadata on a closed candidate breaks the bracket (spec:1503);
  - an extra candidate reacquisition is absent from the table and from the
    cost and scratch accounting;
  - a third descriptor is forbidden (spec:709, 1664);
  - metadata before final admission breaks the order (spec:307-309).
- **At finalization.** Replaying the latest report releases the pair that must
  be held through commit. Replaying an earlier report publishes a spelling that
  was never replayed. That is coherent only if membership attaches to identity,
  and the spec does not say so.
- **Unstated.** Which contexts need a replay:
  - roots and witnesses;
  - listed app candidates inside an admitted root;
  - link and registration targets;
  - each current turn's fresh report — "reapply …region policy" (spec:1148-1149)
    and "Reapply policy to every fresh report" (spec:584).

  For roots, how the replayed object becomes the listing stream held on a root
  credit is also unstated.
- **What needs settling:**
  - which contexts replay;
  - which report is replayed, and whether membership attaches to identity or to
    the finalized spelling;
  - replay rows in the k119 table and the inspection view, with how the metadata
    bracket is re-established and what it costs;
  - acquiring a root stream after its replay.

### P2 — An unknown mount is opened to classify it, outside any consent policy (medium)

spec:445-447: "an open needed to obtain mount metadata is transit and still
requires pre-open protected/cloud policy."

- **Policy coverage.** The pre-open policy covers only home protected and
  known-cloud identities (spec:488-513). The repository's own protected-path
  evidence records "Removable/network volumes: unavailable, not passed"
  (`docs/design/architecture/workspace-inspection.puml:26`; caption at
  `diagrams.json:166`). Neither class is in the policy or in the list of
  dialog/hydration observers (verification:116-119, 157; spec:2081).
- **No open is needed.** The no-follow `fstatat` probe already reports the
  child's device (spec:405-407). A device that matches no established startup-pair
  or Preboot witness is therefore known to be unadmitted before any open.
- **Routes that reach a foreign mount:**
  - registration URLs, which cover every Launch Services registration, including
    apps on external disks, mounted installer images and network shares
    (spec:1505, 1585-1586);
  - `.app` link targets and symlinked roots;
  - queued descent into a nested mount found while listing home, such as a FUSE
    or sshfs mount or an attached image, because the same walker performs queued
    reacquisition (spec:390-392).
- **Consequence.**
  - A consent dialog at a transit open is an acceptance failure that the design
    walks into rather than avoids.
  - A network or FUSE mount root can block the open indefinitely. That holds a
    worker and its credits, and beside any resource failure it disables search
    until restart (spec:1712-1720). A stale registration unrelated to the query
    can trigger it.
- **What needs settling:**
  - refuse an unestablished device before any open, with a reason derived from
    the probe, or name these consent classes in the pre-open policy;
  - add removable, network and disk-image subjects with dialog observers;
  - state the effect on registration negatives (a refused URL already prevents
    UNREGISTERED, spec:1541-1543).

### P3 — A symlinked protected or cloud policy route has no defined witness outcome (medium)

spec:493-497 says that a policy-route symlink "supplies no target identity; its
literal target can add a known blocked spelling …, and a required unestablished
alias proof cannot be dropped". Two rules bear on it:

- "Unknown relevant lookup/identity means INSPECTION_FAILED" (spec:510-511).
- Textual folding never authorizes an open; native identity is the alias proof
  (spec:481-482, 505-509).

These routes are not exotic:

- File-Provider-era cloud clients commonly leave a home-level link into
  `~/Library/CloudStorage/…`.
- iCloud Desktop & Documents has used links into `~/Library/Mobile Documents/…`.
- Users relocate Documents or Downloads by symlink.

The spec never says when the target's alias proof is "required", nor how far
refusal reaches when that proof is unestablished. Two readings follow, and both
are defects:

- **Strict.** The target identity is required but never acquired by design.
  Every dependent child decision is then INSPECTION_FAILED, and home search fails
  for these users — even though a target in Library is already covered by the
  Library identity.
- **Lenient.** The target is blocked only by its literal spelling. For an
  ordinary target such as `~/Documents → ~/Work/Docs`, the variant `~/work/docs`
  or a Data-volume route passes the identity check and is opened. That is the
  textual proof spec:481-482 forbids, so C8 reopens for link targets.

The subjects mention "symlink-component aliases" (verification:157) but give no
outcome.

- **What needs settling:**
  - a rule per target class: a target beneath an established blocked identity
    needs no further proof;
  - otherwise, either acquire the target's identity by a metadata route that is
    accepted as prompt-free, or state literal-only blocking as a named limit;
  - the refusal scope;
  - subjects for cloud-style links and for a relocated-Documents link with
    variant spellings.

### P4 — Search returns locations its handoff cannot act on, reported as not found (medium)

- **What search returns.** Locations of up to 8,192 bytes for every entry kind
  (spec:595-596, 667-672), and app paths beyond PATH_MAX (spec:616-618).
- **The handoff.** It copies them unchanged into launch, reveal, open and Zed
  (spec:2271-2275), and the brief routes selections through launch-and-open.
  Those operations inspect a target only through the measured prompt-free route
  of `realpath`, `stat` and three resource values (launch:68-71, 474-480, 546).
  Those calls take PATH_MAX-limited arguments of 1,024 bytes (verification:20).
- **How the failure is classed.** "A name too long to exist" is PATH_NOT_FOUND
  (launch:478-479, 546; `docs/client-guide.md:708`, 764).
- **Counterexample.**
  - A 1,500-byte file found by search goes to `workspaceOpenPath` or
    `workspaceRevealPath`. `realpath` fails with ENAMETOOLONG, and the result is
    PATH_NOT_FOUND or `failed`.
  - A constrained launch at an `applicationPath` over 1,023 bytes cannot
    establish identity.
  - The 1,024…8,192-byte band, which the canonical and resolver design exists to
    keep (spec:769-771), is selectable but not actionable. The client is told
    that a path search has just observed is missing.
- **Disclosure.** None in the handoff, the guide, the trace or the subjects. The
  gap predates k122 (k108 kept 8,192-byte values), but k122 widened returned long
  locations to every entry kind.
- **What needs settling:**
  - the actionable length and how a client sees it;
  - the route: per-result disclosure, a launch-and-open change in that
    increment, or the loss sent to k93;
  - a subject that acts on a long search result.

### P5 — A size refusal from a lengthened spelling still stops the root after independent proof (low-medium)

The rules involved:

- Each listing turn reacquires the stored location with A/B, compares identity
  and association, and then calls the reported-path operation (spec:555-560).
- Byte differences alone prove neither movement nor failure (spec:578-580).
- At dequeue, a full-buffer ENOSPC with an independently unchanged parent is an
  exact SUBTREE (spec:607-611, 753).
- A native-size refusal on a current stream stops the whole root (spec:749).

- **Counterexample.**
  - A dequeued directory whose report fits at 8,180 bytes becomes the current
    stream.
  - Between its turns, an ancestor's vnode is recycled and re-created by another
    process's NFD lookup. Names come from the creating lookup (k110 C2), so the
    next report needs more than 8,191 bytes.
  - The reacquisition has just proved identity and association unchanged.
    Nevertheless, spec:749 stops the whole home root, losing every queued sibling.
  - The same native fact one turn earlier would have been an exact SUBTREE.
- **The walk.** Every transition rechecks A's reported location (spec:408-409),
  so a lengthened ancestor spelling becomes a shared-prefix refusal.
- k110 C2 named exactly this root stop. k122 repaired only the dequeue position.
- **What needs settling:**
  - route by independent proof, as dequeue does, or justify the root stop;
  - state what the per-transition report of A establishes, given that byte
    differences prove nothing.

### P6 — Native ELOOP is classed as a link loop, but the walker never follows links (low)

- spec:463 makes "Native ELOOP or hop exhaustion" INSPECTION_FAILED "with bounded
  loop/hop guidance".
- Every open is a component-wise no-follow open (spec:396-411, 702-704). Under
  macOS `open(2)`, ELOOP with O_NOFOLLOW means the final component is a symlink.
  After the probe saw a directory, that is a type change between probe and open.
- spec:415-418 calls a newly encountered link a changed association. So one
  observation gets two classes, and the loop guidance misleads the client.
- **What needs settling:**
  - treat a no-follow ELOOP after a directory probe as the context's change
    outcome, or re-probe it as a link where links are permitted;
  - keep loop guidance for expansion 33.

### P7 — The application-identity ADR re-acquires file-search traversal mechanics (low)

- `docs/adr/application-search-uses-bundle-identity.md:20-29` now records
  several mechanics:
  - queued tasks retain listed locations and identities;
  - descendants use fresh reports;
  - exact-path deduplication leaves distinct strings.
- k121's C9 verdict kept private mechanics in the spec, and the coverage ADR
  keeps them off its public slug. These lines are file-search traversal detail
  in an application-naming record, and they will go stale against the spec.
- **What needs settling:** keep only the naming consequence — a retained
  identity keeps its first finalized reported spelling, with no alternate — and
  cite the spec for the rest.
