## Findings

Producer `913613ae98c1` (native-discovery-k202 closing native-discovery-k199),
with k200 `41b39385c8ca` and k201 `0e9aa58d9f35`. Severity orders the list. The
three high findings change a durable posture or make a designed operation
fail as written; the rest are contract or acceptance corrections the
integration can apply in place or route to the named downstream leaf.

### N1 — A GraphQL client can now trigger Koine's OS consent dialog, contradicting the unreconciled Machine and client-guide rule (high)

- Machine states "Only its UI requests OS consent … ModalAnyware … does not
  request Koine's permissions for itself" (docs/specs/machine.md:67-72); the
  client guide says "A client never asks for Koine's OS permission itself"
  (docs/client-guide.md:322). The design adds
  `Mutation.workspaceRequestSettingsAutomation` under workspace:control alone,
  calling `AEDeterminePermissionToAutomateTarget(askUserIfNeeded=true)` (spec:59,
  283-301; trace docs/specs/workflow-providers.md:199), and the same guide now
  offers it to clients (client-guide.md:405-408). Neither earlier rule was edited
  and the tension is not raised anywhere.
- k201's permission is "a separate explicit consent/setup operation"
  (docs/requirements/modaliser-workflows.md:66-73); it does not settle who may
  trigger the dialog. The earlier rule exists so consent is requested by Koine's
  own explaining UI, not by any process holding a bearer token. As designed, any
  workspace:control client can raise "Koine wants to control System Settings"
  at a time of its choosing — the consent-UI route docs/adr/provider-authority-follows-effects.md
  refuses for input/menus ("native UI control must not become a second route to the
  local-console principal").
- The consent scope is also misstated. The SDK says a consenting user lets
  "this application … send events to the target" (AppleEvents.h, SDK 27,
  lines 331-336): Automation consent is per (Koine host, System Settings), not
  per event. CONTEXT.md:149-152 ("one fixed System Settings read or reveal
  event's OS permission"), spec:59 and the disclosure wording imply a per-event
  grant; once granted, every Koine provider in the host process can send any
  Apple event to System Settings.
- **Consequence.** Put the trade-off to Antony: client-triggered setup under
  workspace:control (then reconcile machine.md:67-72, client-guide.md:322 and
  disclose the target-wide consent), versus setup initiated only from Koine's
  own UI with the client directed there (the existing Accessibility pattern).
  Either way correct the per-event framing in the glossary, spec and disclosure.

### N2 — Reveal's required activation has no workable primitive (high)

- Reveal must "request activation of the still-validated process once" after the
  reveal reply (spec:323-326), and "a failed activation … returns failed with
  effects ambiguous" (spec:331-332). No primitive is named in the spec, trace
  (workflow-providers.md:200), allowlists (spec:459-465) or N4 (acceptance:78).
- Koine's own record: `NSRunningApplication.activate(options:)` returned `false`
  for Koine as a background service; `activateIgnoringOtherApps` has no effect
  from macOS 14; `activate(from:options:)` needs the active app to yield
  (docs/verification/desktop-focus-vm.md:64-75;
  Providers/DesktopProvider/Sources/DesktopProvider.swift:458-467; SDK
  NSRunningApplication.h:27, 133-148). The desktop provider therefore uses
  `AXFrontmost` under Accessibility — a route the new images forbid ("no … AX …
  anywhere", spec:461-462).
- **Consequence.** As designed, the AppKit route the allowlist hints at
  ("activate calls", spec:463) predictably makes every acknowledged reveal end
  `failed`. Choose and pin a primitive — for example Launch Services
  `openApplication(activates=true)` on the validated running bundle, the existing
  launcher's accepted route, stating its race-to-launch semantics — and carry it
  into the authority rows, the settings allowlist, N2/N4 and V7.

### N3 — Workspace disclosure is falsified and the prior host can serve native surfaces under it (high)

- The core-owned disclosure says "Launching, opening and revealing also need
  desktop:control … neither capability works without the other"
  (Sources/KoineCore/CapabilityDisclosures.swift:15-23; machine.md:1423-1445). The
  design makes workspace:control alone sufficient for background launch and
  consent prompting (spec:58-59), adds workspace:read with no disclosure entry,
  and states "Existing launch/open/document-handler disclosures remain complete"
  (spec:75).
- Disclosures live in the host core, not the provider. The current
  selection-aware host (bundled workspace 1.0.1) admits per-user updates that
  declare additional-capabilities-v1 and first-party-selection-v1 — exactly what
  the new provider declares (spec:485-486). A per-user 1.2.0/1.3.0 native update on
  that host is selected and serves read, prepare, setup and reveal while the
  grant UI shows the old text. Acceptance names "compatible prior selection-aware
  additional-capability host/new 1.2.0 provider" as an expected-working pairing
  (acceptance:41-42), but no profile pins the realistic
  prior-host-plus-per-user-native-update composition; the only prior-host profile
  is the refusal (machine.md:1813).
- The trace assigns the new disclosure to app-and-file-search "before version
  1.2.0/schema 1.1.0 ships" (workflow-providers.md:228-232), yet no G/N/V row or
  live k7 charter carries it; only baseline k17 checks disclosure generally
  (baseline-acceptance-k17's Done when, "Grant disclosure is accepted…").
- **Consequence.** Either require a new host feature that only a
  disclosure-capable host declares (so prior hosts refuse native updates, with a
  pinned refusal profile), or record an explicit decision accepting
  under-disclosure on prior hosts with its profile. Rewrite the workspace:control
  text, add workspace:read, and add a disclosure acceptance row (cf.
  docs/verification/workspace-disclosure-vm.md) owned by k7/k30.

### N4 — Application breadth bounds are unreconciled and bind arbitrarily on real machines, out of reach of acceptance (medium-high)

- Per job: 2,048 candidate URLs and retained choices, but only 256 identifier
  expansions including Safari/Finder, and 16,384 native calls that also pay every
  descriptor-relative lookup step (spec:413-416). Each candidate needs a
  component-by-component walk plus bundle reads, and each registered copy compared
  needs its own walk (ApplicationStage.swift:63-87 shows the existing per-copy
  cost). No document derives any of these numbers or reconciles them; the call
  budget plausibly binds well before 2,048 candidates.
- Admission is "bounded round-robin … promises no rank/fairness" (spec:405-406),
  so on overflow the surviving set is arbitrary. Apps whose identifier misses
  the 256 expansions are UNKNOWN (spec:185), and the guide makes UNKNOWN
  "reveal/copy choices" only (client-guide.md:392-393): an arbitrary subset,
  possibly configured launchers, becomes unlaunchable. That is k197 T2's
  arbitrary-native-order sample, now for applications.
- The breadth source also admits non-user-facing bundles that spend the budget:
  generic `runningApplications` includes agents such as Dock or loginwindow, and
  index results can include nested helper bundles. The choice exposes no native
  fact (activation policy, LSUIElement/LSBackgroundOnly, nesting) for the client
  filtering the design delegates. Modaliser's own source was the same index
  query with no cap (Modaliser/Sources/Modaliser/AppScanner.swift:16-46).
- V2 runs on a sparse VM and N5 uses synthetic edges, so no subject can show the
  caps binding on a realistic population.
- **Consequence.** Derive the caps from a declared population subject, decouple
  registration from a cap smaller than the retained set (or bound it per retained
  choice), make the overflow choice non-arbitrary or diagnostic, expose or apply a
  user-facing-app fact, and add a populous-catalogue V subject.

### N5 — Catalogue registration semantics diverge from the action's accepted rule (medium)

- The catalogue derives INSTALLED/UNREGISTERED from
  `LSCopyApplicationURLsForBundleIdentifier` and treats a preferred
  `urlForApplication` copy outside that list as a contradiction that blocks
  INSTALLED and UNREGISTERED (spec:181-191).
- The action re-resolves with `NSWorkspace.urlsForApplications` plus the
  preferred copy as an extra candidate (NativeWorkspace.swift:10-17;
  ApplicationStage.swift:56-68), because VM evidence showed the two answers
  disagree and a list-only rule refused an eligible copy — a defect found and
  fixed (docs/verification/application-installations-vm.md:154-215).
- INSTALLED is what the guide lets a client launch (client-guide.md:390-393), so
  the catalogue is predicting the action's outcome with a different API and a
  rule the action already rejected. No G/N/V case pairs a catalogue state with
  the action's result for the same copy (V3/V4, acceptance:95-96).
- **Consequence.** Define INSTALLED as "the existing constrained selection would
  select this copy", computed by the same procedure and APIs (or prove the APIs
  equivalent), and add paired catalogue/action cases including a preferred-only
  copy.

### N6 — An empty or partly-built index can be published as an AVAILABLE, COMPLETE breadth source (medium)

- A gathered empty index is "a valid empty INDEXED_APPS observation" when
  "qualified completion signal and parsing conditions hold" (spec:362-364), and
  AVAILABLE allows a "qualified complete empty declared observation domain"
  (spec:354). The qualifying conditions are not defined.
- Every supported macOS has indexed system applications, so an empty or
  system-app-less index observation signals indexing off, excluded or
  rebuilding — not a healthy empty. With the Safari/Finder registration seeds the
  root is nonempty and reads AVAILABLE, with INDEXED_APPS availability AVAILABLE.
  That is the fabricated availability the Done-when forbids.
- The design already has the contradiction evidence: registration-found system
  apps absent from the indexed set. V2/V8 include no index-disabled, excluded or
  rebuilding subject.
- **Consequence.** Classify an empty, or registration-contradicted, indexed
  observation as UNKNOWN (or PARTIAL with a named diagnostic), state the rule, and
  add a V subject with indexing disabled or rebuilding.

### N7 — Settings completeness right after preparation, and lazily populated anchors, are unqualified (medium)

- Prepare returns RUNNING for "process readiness, not useful-catalogue …
  readiness" and the client "explicitly follows with workspaceSettings"
  (spec:258-260). A read shortly after a cold launch can see a pane list that is
  not yet populated but identical across both ID reads, so the
  CHANGED_DURING_DISCOVERY guard (spec:211-213) does not fire; the result is then
  COMPLETE over RUNTIME_EXPOSED_PANES with missing panes. "Empty runtime
  pane/anchor list can describe its declared interface if qualified"
  (spec:366-367) leaves "qualified" undefined.
- Anchors may be filled only once a pane's extension loads; a reply of `[]` then
  reads as a checked empty list (spec:233; SDL:80).
- The read is 2N+2 serial preflighted round trips within three seconds
  (spec:209-224, 403-405). The dictionary's inherited `properties` form
  (CocoaStandard `item`) could keep association in a single reply, but it is not
  weighed.
- V5 checks preparation and V7 inventory, but no row reads immediately after a
  cold prepare versus warm.
- **Consequence.** Define a readiness/quiescence rule (or report UNKNOWN when it
  is unmet), qualify anchor population, and add cold-versus-warm read rows to V5/V7.

### N8 — Long application locations: the type check makes them unpublishable, and launch-and-open's handoff subject becomes unconstructible (medium)

- "Every published app needs a checked native application-bundle type"
  (spec:161), and the only defined type check is the whole-path
  `isApplicationKey` resource value
  (docs/specs/workspace-launch-and-open.md:870-873), which the spec forbids past
  path limits (spec:167-169). It also withholds whole-path bundle metadata, hence
  the identifier, for long locations. Yet it promises to "preserve
  representable long locations" (spec:167).
- launch-and-open now requires app-and-file-search to show "an observed long
  application location … its unchanged selected identifier/location receives
  this refusal" (workspace-launch-and-open.md:599-604, 766). Without a type or an
  identifier, the catalogue can produce no such selection, so that pending
  subject can never pass and would hold baseline open.
- **Consequence.** Specify a descriptor-relative type/identity source for long
  candidates, or restate the handoff subject (for example through reveal or copy)
  with an explicit decision, and make spec:161 and spec:167 agree.

### N9 — The setup result cannot express the outcomes acceptance and clients need (medium)

- `WorkspaceSettingsAutomationResult` has only ALLOWED/DENIED/UNAVAILABLE and
  free-text guidance (SDL:144-151). The spec's "UNAVAILABLE/SETUP_UNSUPPORTED"
  (spec:289) has no field, so stopped target, unsupported host posture, refused
  or changed target and capacity refusal collapse or become root `failed`. V6
  requires "denial, revocation, unsupported posture, stopped target, refused
  target and late consent remain distinct" (acceptance:98), and clients may not
  parse guidance.
- A human answering the dialog usually takes longer than the five-second core
  cutoff (machine.md:168, 177-181; spec:296-299), so setup's success path
  normally ends `failed`. The guide gives no follow-up protocol, such as
  re-running setup, which then returns ALLOWED/DENIED without prompting.
- After DENIED, revealing the Automation privacy pane is itself blocked (reveal
  needs READ and REVEAL permission, spec:316-317), so Koine has no route to the
  remedy.
- **Consequence.** Add a closed reason field to the setup result (same authority
  set), state capacity and deadline outcomes, and document the post-deadline and
  post-denial client protocol.

### N10 — The principal image is outside every guard, and the action adapter seam is injectable (low-medium)

- The design puts allowlists on the action, discovery and settings images and
  forbids the action image receiving effect-capable callbacks "from the
  discovery/settings images" (spec:454-466). The principal — the bundle
  executable that links all three and routes every resolver — has no stated
  allowlist or control, and the contract view draws no guard edge from it
  (docs/design/architecture/native-discovery-contract.d2).
- The action module takes its native adapter by injection
  (WorkspaceProvider.swift:59-67; Factory.swift:12). After the split, a
  principal-constructed `WorkspaceNative` that wraps settings launch or activation
  would pass every action-image import, selector and link check.
- **Consequence.** State that the production adapter is constructed inside
  WorkspaceActions with no public injection seam, give the principal its own
  allowlist, and add a principal-injection failing control to N2 (k127 owns the
  construction).

### N11 — The four-image packaging decision has no ADR (low)

- Splitting workspace into principal/actions/discovery/settings images is hard
  to reverse (loader verification, guard instruments, release checks;
  machine.md:1345-1356), surprising without context, and settles a real
  trade-off with a rejected single permissive image (spec:39-44). It meets the
  ADR AND test but lives only in the spec. If N1 lands on client-triggered
  consent, that posture also earns a record.
- **Consequence.** Add a slug ADR (or extend
  provider-authority-follows-effects) and cite it from the spec and trace.
