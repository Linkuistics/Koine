## Findings

Producer `165b6a430dfe` (native-discovery-k209 closing native-discovery-k205).
Severity orders the list. Each is something the complete design would do
wrongly as written, before any native behavior is known.

### R1 — The 64-diagnostic gate is underived, and exhausting it now discards whole catalogues (high)

- Diagnostics are capped at 64 per job, one reserved for DIAGNOSTIC_LIMIT
  (spec:713, 676), and both certificates budget exactly 64 (65,536 Settings
  diagnostic bytes, spec:754; 64×2,048 application bytes, acceptance:303).
  k206 made diagnostic exhaustion population-fatal for applications
  ("entry, identifier, call, copied-value, diagnostic or deadline exhaustion
  invalidates application publication: status FAILED, items null", spec:221-223),
  and G10 enshrines it as the expected outcome (acceptance:84). For Settings,
  "population-wide owned-limit … exhaustion … always withholds staged items and
  returns FAILED" (spec:643-645).
- The same design requires a diagnostic **per item** in ordinary cases:
  refused/unidentified candidates (spec:260), missing labels (spec:128-129),
  supplements' missing or conflicting identifiers (spec:200-201), malformed or
  refused flag metadata (spec:366-367), every INDEXED_ITEM choice's unsupported
  bundle facts (spec:310-311), and a pane-scoped diagnostic for **every** pane
  whose anchors are empty, refused or unestablished (spec:450-451, 479).
- Neither envelope reconciles these: 2,048 choices and 256 panes against 63
  usable records. Stale index entries, bundles in protected locations or
  index-only nested helpers can pass 63 on an ordinary Mac, and a cold Settings
  read whose anchors are lazily empty (the very case k207 designed for) emits
  one diagnostic per pane. Losing a diagnostic does not let native order choose
  survivors, so the no-prefix rationale (spec:241-250) does not cover making
  it fatal.
- **Consequence.** As written, P1024/V11 and V12 can fail by design and be
  misrouted to k93 as native gaps, and a user loses every app (launchers
  included) or every pane. k205's first clause ("derive coherent … bounds from
  declared finite population subjects") is unmet for this bound. Derive the
  diagnostic budget from the subjects, or make per-item diagnostics bounded and
  non-fatal (for example aggregated by reason, with counts), and correct the
  certificates, G4/G10 and N5 together.

### R2 — The localized-name read reaches past the boundary that k208 derived from Info.plist alone (medium)

- The BUNDLE_RESOURCE route supplies "type and optional **localized**
  name/identifier" (spec:254-255) through the "admitted Bundle
  identifier/info/localized dictionaries" (sources:228-229). The indexed route
  is chosen only when the bundle path or its 20-byte Contents/Info.plist suffix
  reaches 1,024 bytes (spec:256-258, 268-272; sources:162-164). The rule is
  "Never call pathname APIs past their applicable limits" (spec:261-262).
- A localized dictionary is read from a longer path:
  `/Contents/Resources/en.lproj/InfoPlist.strings` is 46 bytes (Base.lproj 48,
  English.lproj 51; measured with `wc -c`). With at most 1,023 bytes before the
  NUL, any localized bundle of about 977–1,003 bytes satisfies the Info.plist
  guard but not its localized read. The existing action never reads a
  localized dictionary (NativeWorkspace.swift:35 reads only `bundleIdentifier`),
  so no accepted evidence covers this.
- L1500 makes the 1,003-byte bundle "the ordinary-reader control"
  (acceptance:166) with "known localized names" (acceptance:153) that must be
  "useful correct" (acceptance:183-184), which is exactly inside that band.
- **Consequence.** The ordinary reader either calls a pathname API past its
  limit or silently publishes an unlocalized or null name. Neither is
  detectable from the 20-byte arithmetic. Derive the BUNDLE_RESOURCE boundary
  from every path the admitted reads actually address (or state which name
  source is used and its path), and move the L1500 control below it, with a
  boundary copy inside the band.

### R3 — Selected reveal treats a lazily absent object as a missing selection, and no subject reveals in an unvisited incarnation (medium)

- The readiness contract says "A get reply can reflect lazy, not-yet-populated
  objects" (spec:411-413), so empty anchors stay null rather than certifying
  absence (spec:450-452).
- Reveal re-resolves the pane by ID and the anchor by name with core/getd, and
  "Positive no-such-object before submission is
  DEPENDENCY_UNAVAILABLE/SELECTION_UNAVAILABLE" (spec:583-587; G8,
  acceptance:82). In a freshly prepared or never-visited incarnation, a valid
  anchor the client kept from an earlier read (its MRU) or from a previous
  incarnation can answer no-such-object only because it has not loaded. The
  operation then reports the destination unavailable: the absence claim that
  the read path refuses to make.
- Every reveal subject runs after the V12 visits: V7 reveals "under V12's
  pre-visit/post-visit protocol" (acceptance:138) and V12 reveals in "that same
  independently recorded visited incarnation" (acceptance:225). None reveals a
  known anchor in a cold, unvisited incarnation, so the defect is not exercised.
- **Consequence.** Carry the lazy uncertainty into reveal's pre-check (a
  no-such-object there certifies no absence), or record why a positive
  no-such-object is authoritative for reveal although it is not for reads, and
  add a cold, unvisited-incarnation reveal of a known pane and anchor to V12/G8.

### R4 — A missed deadline in the confirmation sweep discards a complete first map, unlike a native failure in that sweep (medium-low)

- The second sweep exists only for change detection and certifies nothing
  (spec:422-427, 440-441). Both sweeps share three seconds (spec:422-424), and
  514 serial preflighted events at the envelope make the deadline the likeliest
  limit to bind.
- A later failed pane read "may retain individually valid positive
  observations under the ordinary partial-result rules" (spec:435-436), and "a
  known native failure, limit, block or stopped target still follows the
  ordinary precedence" (spec:453-454). But Settings deadline exhaustion "always
  withholds staged items and returns FAILED" (spec:643-645, 709; G4,
  acceptance:78).
- A complete first sweep is not a native-order prefix, which is the rationale
  for global FAILED (k207's "never a staged prefix"). So a timeout during
  redundant confirmation turns a complete honest map into FAILED/null, while a
  native error at the same point keeps PARTIAL results, and spec:453-454
  contradicts spec:643-645 on which rule a limit follows.
- **Consequence.** State which outcome a deadline after one complete sweep
  produces and reconcile the two precedence sentences. If the complete map
  survives, publish it as PARTIAL with TIME_LIMIT and readiness uncertainty;
  otherwise record why losing it is preferred. Test the case in G4/N5.
