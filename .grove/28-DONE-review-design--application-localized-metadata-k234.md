### R1 — P1024 fixes cardinality but not the metadata dimensions that drive the gate, so a pass cannot establish the useful-population claim (high)

- **Contract.** Release needs P1024's "1,024 useful identifiers (fourteen
  configured/system witnesses and 1,010 distinct signed UI apps)" within
  20,971,520 gross (`qual`:262-264, 297-301); `acc`:348 says only "1,010 distinct
  signed UI test apps"; application-population.json:86 requires P1024 to *measure*
  its metadata/localization dimensions, not to make them representative. `ws`:249-252
  treats P1024 as the stand-in for an ordinary measured population.
- **Evidence.** In the committed grouped packet (en-AU,en; known local gross plus
  both walk subterms) the 290 `/System` spellings cost 8,887,073 bytes (mean 30,645)
  — 42% of the gate before any useful third-party app; the 350 installed non-system
  apps average 14,809 (median 5,490); the 1,403 disk-only fixtures average 3,752.
  Known local gross alone: real rows 20,818/row versus fixtures 2,293/row. The
  subject's fixtures add ~194 information bytes and ~3 locale records each
  (application-metadata-subject.md:118-122).
- **Failure.** A supported VM's system baseline plus 1,010 fixture-shaped apps can
  pass every gate while a machine with the same cardinality of real third-party
  apps (≈4× the fixture cost on average) fails closed as FAILED/null. "P1024
  qualified" would then certify a population shape no real user has.
- **Consequence.** The selected route exists to supply the evidence analytic fit
  could not; with unconstrained fixture shape it can pass without supplying it.
  Pin the P1024 fixture metadata distribution (information/name-file bytes, direct
  locale count, loctable keys) to the measured real distribution or an explicit
  stated envelope, and say which population shape a pass qualifies.

### R3 — Qualification measures an instrumented private image, but nothing carries its evidence to the shipped image (medium)

- **Contract.** "Qualification instrumentation's provider-owned raw requests/writes
  and explicit calls also count; retain its identity and perturbation in the
  evidence" and "Production exports/linkage contain no test injection" (`qual`:202-207);
  private builds "do not establish a production native-provider baseline"
  (`ws`:482-484); release then proceeds "through the usual consumer acceptance"
  (`qual`:233). N5 must pair every charged operation to the actual binary (`acc`:142).
- **Evidence.** No rule states whether receipt instrumentation ships, or how
  N5/N8 evidence from the instrumented image transfers to the uninstrumented one.
  The repo's own precedent, docs/verification/search-serviceability.md:252-259,
  requires an ordinary / hooks-disabled / hooks-enabled equivalence comparison and
  limits the evidence to "the instrumented subject".
- **Failure.** Either the production image cannot produce N5 receipts (so its
  acceptance cannot meet N5), or qualification evidence describes a different
  image from the one released.
- **Consequence.** The in-provider receipt recorder is effectively a fourth test
  seam beside the three agreed ones. Declare it, and state the equivalence or
  re-qualification rule that binds the release image — reusing the existing
  three-build comparison is the obvious candidate.

### R5 — The cost of a refused admission check is reserved nowhere, so the attempt gate can be exceeded (medium)

- **Contract.** Comparisons are explicit attempts (accounting ADR line 8); "The
  actual compiled adapter's guard arithmetic, checks and raw bookkeeping also
  count" and "W includes guard and receipt bookkeeping" (`qual`:51-52, 73); equality
  admits (`qual`:67).
- **Evidence.** A refused transition's W is never admitted, and C, E and the
  terminal reservation (`qual`:54-55, 61-63) do not name the evaluation that
  refuses: its checked additions, comparisons, deadline clock read and liveness
  check. The pure model returns a free refusal (`checker`:65-76), so no control can
  see the gap.
- **Failure.** After an admission that lands exactly on 4,194,304 reserved
  attempts, the next evaluation's own operations push actual attempts above the
  gate although nothing further was admitted; deadline-triggered refusals do the
  same.
- **Consequence.** Small in magnitude, but it breaks the exact invariant release
  checks and the "no omitted explicit operand" claim. Reserve one guard evaluation
  in the terminal bookkeeping (freeze is sticky, so one suffices) and model it.

### R9 — The public outcome of a failed explicit cleanup is undefined (low)

- **Failure.** "Prevents acceptance" governs qualification only. In production, a
  failed `close` or release after a complete tree leaves open whether the catalogue
  publishes, becomes FAILED with a closed reason, or adds a diagnostic, and whether
  a client can observe it at all.
- **Consequence.** One unspecified branch in a construction claimed complete.
  State the public result and reason, and how the qualification observer detects
  it at the agreed seams.
