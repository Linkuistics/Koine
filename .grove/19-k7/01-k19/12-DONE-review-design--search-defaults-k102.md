## Findings

Anchored to producer `44233e3defc0` (`search-defaults-k101`). Coordinates are
the current working copy after `9694eb72a071` (k99, `.grove/` only) and
`b567283886a3` (k103, shared spec/SDL/guide/glossary/view text). `spec` is
`docs/specs/workspace-search.md`; `ADR` is
`docs/adr/search-coverage-describes-observations.md`. Host observations are
read-only inspection of this Mac (macOS 26.6.2/25G83), not acceptance.

### D1 — The held-stream descriptor ceiling exceeds the process table that search shares with the listener, store and other providers (high)

spec:567 holds up to 32 streams per root; spec:782-786 totals 512 (+2) per job
and 2,056 for four jobs, "ceilings, not an assurance that the OS admits that
many"; spec:634-637 and 786-788 say a refused descriptor freezes "the affected
root". ADR:28-30 weighs descriptors only as a cost to search itself.

- launchd's default soft `maxfiles` on this host is 256 (`launchctl limit
  maxfiles`). Koine launches through LaunchServices/`SMAppService.mainApp`
  (`Sources/KoineApp/LoginLaunchView.swift:15`). No source, doc or grove note
  sets or reads `RLIMIT_NOFILE`. A launch from a shell inherits a raised limit,
  so dev runs and normal launches differ.
- Providers load in-process (machine.md:1083). Search therefore shares one
  descriptor table with the SwiftNIO loopback listener
  (`Sources/KoineHTTP/LoopbackListener.swift`), the grant store, other providers
  and launch/open actions.

Consequences:

- One job over eight deep client roots can already need the whole default table.
  The 16-root × 32-frame subject (spec:742-744) cannot reach its 512 ceiling in a
  normally launched Koine.
- EMFILE is not root-local. Whichever thread opens next fails: an accept, a store
  write, another provider, an action, or a root of another search job. "Freezes
  the affected root" describes only the search thread that happens to observe it;
  a sibling job's root is frozen for descriptors another job holds.
- A client holding only `workspace:read` can issue 16 deep roots under four
  aliases, re-issued every three seconds, and deny unrelated control and
  management work. spec:780-781 states unfairness for the worker pool only, not
  for the process table. The VM row (spec:891) checks search's own refusal, not
  that other Koine paths stay serviceable.

Smallest coherent correction:

- Make descriptors a Koine-owned, process-wide search account, sized below the
  effective soft limit read at start, with an explicit reserve for non-search
  work and no limit change. Acquire from it before each open, like the other
  accounts.
- Decide what traversal does when a root's credit is exhausted. A counted,
  affecting reason in a reserved root group is better than a whole-root stop.
- Restate spec:782-790, the ADR and the workflow trace
  (`workflow-providers.md:254`) against that account.
- Add a VM case on a normally launched host showing that listener, store and
  actions stay serviceable while search is saturated.

D2's order choice changes how large this account must be.

### D2 — Depth-first order exhausts the real home's root budget inside one early branch, so shallow names are never examined (high)

spec:612-619 traverses depth-first in native entry order. spec:655-658 concedes
the early-branch bias. It reopens the choice on "a review or actual-adapter
evidence showing … lost required witnesses". The realistic home row (spec:730)
has 15,397 entries; the early-branch row (spec:736) mentions only "a later
sibling marker".

Evidence from Antony's configured home on this host. Order is the native
readdir order (`/bin/ls -f`). Counts come from `find`, with name-based hidden
pruning and approximate package pruning; protected names were never entered.

- Home's children start Music (2,395 entries), go (7,311), Archive, bin,
  Development. `~/Development` alone holds more than 400,000 visible entries.
- Inside Development (36 children), the roughly 90,000 remaining entries run out
  inside child 12, `grove.improve-initial-design-decomposition-skill`, which holds
  more than 200,000 entries.
- Even before the three-second wait, default file search never examines:
  - Development children 13–36, including ModalAnyware, Modaliser, TestAnyware
    and this workspace;
  - the depth-1 directories Pictures, Zotero, Sites, Public, Movies,
    Applications, quicklisp and src;
  - depth-1 files such as `nix-migration.md`.

  These are what "open in Zed" and reveal target. The observed native order is
  neither alphabetical nor recency, so which shallow names survive is the
  arbitrary native-order sample spec:33 and spec:50-51 refuse.
- Modaliser's intended result is explicit: `Sources/Modaliser/AppLibrary.swift:176-178`
  indexes the root's children first "so top-level directories … are never
  crowded out by a depth-first deep dive into earlier siblings". k101 reintroduces
  that failure.

The k101 brief asked to weigh FIFO "against depth-bounded traversal and bounded
root-level aggregation for frontier/depth exclusions". spec:649-658 and
ADR:34-39 weigh only larger queues, LIFO with four streams, and close/reopen.

Two options are unweighed:

- breadth-first with one reserved root FRONTIER_LIMIT DESCENDANT_GROUP, the
  aggregation now used for depth. It removes k98's R2 per-parent cutoff and keeps
  shallow-first coverage with few open streams.
- iterative deepening over held streams.

On this home the bound binds whatever the order, so the order decides which
names are found. DFS is the order that loses the shallowest.

Smallest coherent correction:

- Weigh shallow-first order against DFS on the measured shape.
- State the ordering property the file workflow needs, for example: every
  eligible name at depth ≤ k is examined before any deeper name, within budget.
- Rework the coverage ADR in place.
- Replace or extend spec:730/736 with a fixture at the measured scale: at least
  400,000 entries, a branch over 200,000 early in native order, and depth-1 names
  after it. Its expected outcome must name those shallow witnesses.

This approves no reduced domain. k93 still decides the omissions that remain.

### D3 — Cancellation closes held streams from outside the worker with no ownership hand-off (medium)

spec:786-790 says "Cancellation closes other idle held streams without racing
the blocked stream". The streams belong to the job's frames (spec:640-645).
While a call blocks the worker, any close of "other idle" streams therefore runs
on another thread. spec:703-707 forbids late commits and new descriptors, but
says nothing about who owns a frame after that close, or what the worker does
when its call returns.

Its unwinding pops frames whose `DIR*` or descriptor were already closed:

- A second `closedir` is a use-after-free.
- A close or `openat` on a descriptor number since reused by the listener, the
  store or another job acts on someone else's file. The store case risks
  corruption.

During a blocked path-based metadata call (spec:832-834) every stream is idle,
so the whole stack is closed under the worker. Neither k96 (`7653465b1173`) nor
k100 (`d77182febb6e`) had such a cross-thread close.

Smallest coherent correction: give each job's stack one owner. Either:

- the worker alone closes its frames once it observes cancellation after the
  call returns, with the account charging them until then; or
- a per-job lock with a closed flag per frame, under which the canceller closes
  idle frames and the returning worker never touches a closed frame or its
  number.

Add a controlled-adapter case: cancel during a blocked call, let the call return,
and assert that no descriptor is closed twice or used after close.

### D4 — Held-ancestor descent diverges from path-based protected policy after a rename, and the recheck follows the open (medium)

spec:640-645 and spec:829-831 open children through the held parent and a
single name, then "revalidate identity/policy/mount before conversion to a
stream". spec:835-838 lists "rename of a held directory" only as a completeness
limit.

k101 removed the "fresh checked no-follow component walk for queued tasks"
(present at `d77182febb6e`). Every descendant open is now relative to an ancestor
held for its whole subtree, interleaved with other roots across the wait.

Suppose the user moves a held ordinary directory, such as `~/Development/x`,
into Documents, Desktop or Downloads during a search:

- the frame paths still read `~/Development/x`, so the path-based policy check
  passes;
- `openat(held, child)` then opens inside a TCC-protected scope;
- the recheck runs after that open, and the open is the potentially prompting
  operation.

The identity comparison (spec:266) catches only the protected directory itself,
not a descendant reached through a moved ancestor. Moving a folder is an ordinary
action, not an adversarial race. The consequence is a consent prompt attributed
to Koine, against the root brief's prompt-free reads.

Smallest coherent correction:

- Before each descriptor-relative directory open, re-derive the held parent's
  filesystem-reported location with the descriptor path operation the identity
  contract already relies on (acceptance must confirm it is prompt-free on a
  moved descriptor). Apply protected/cloud policy to that location, and refuse
  with CHANGED_DURING_SEARCH when the parent has moved.
- State the remaining check-to-open window as a prompt-risk limit.
- Add a VM case that moves a held ancestor into Documents mid-search and checks
  for any dialog.

### D5 — The Preboot bullet maps unknown identity or classification to UNSUPPORTED_VOLUME, contradicting k103's failure class (medium-low)

spec:154-155 reads: "Unknown identity or classification is UNSUPPORTED_VOLUME".
k103's text says otherwise:

- spec:148-150: uncertain resolution is INSPECTION_FAILED unless "established …
  unsupported classification" applies;
- spec:163-165: "Established unsupported classification uses UNSUPPORTED_VOLUME";
- spec:380-383;
- the SDL status description.

spec:193-195 also says "inability to classify a volume is UNKNOWN". The reason
table (spec:374-378) puts the two readings in different classes:

| Roots, with Preboot identity unknowable | spec:154-155 reading | k103 reading |
| --- | --- | --- |
| Explicit `[Desktop, Cryptex anchor]` | BLOCKED | FAILED |
| The Cryptex anchor alone | DEPENDENCY_UNAVAILABLE, a stable domain exclusion | FAILED |

k103 said its clarifications leave k101's admission predicates unchanged, and
they do. The reason assignment, however, is shared text left to this review.

Smallest coherent correction: at spec:154-155, give unknown identity or
classification INSPECTION_FAILED. Keep UNSUPPORTED_VOLUME for established
non-matching classification. Acceptance row spec:947 already expects that.

### D6 — Two public canonicalization routes disagree on firmlinked spellings, and only the bundle route is fixed (low-medium)

Roots use "the canonical metadata-resolved root" via "native resolution"
(spec:262-266). Application bundles use "a lossless filesystem-reported path",
with the descriptor path operation as candidate route (spec:502-505). On this
host the two disagree for one (dev, ino):

| Input | `realpath` | descriptor path |
| --- | --- | --- |
| `/System/Volumes/Data/Applications` | unchanged | `/Applications` |
| `/System/Volumes/Data/Users/antony/Development` | unchanged | `/Users/antony/Development` |

Both inputs are admitted by identity (spec:266). Consequences:

- Overlapping roots `[home, /System/Volumes/Data/Users/<user>]` (spec:345-349)
  return one file twice under exact-path dedup, each with one rootIndex and its
  own slot.
- `permissionTarget` spellings differ per root.
- An `applicationPath` can lie outside its own root's `resolvedPath`.
- A direct-route bundle path formed by joining `resolvedPath`, the natural
  reading for a readdir child, trips the first-observation rule (spec:513-515):
  CHANGED_DURING_SEARCH on an unchanged filesystem.

The VM column of spec:972 inspects link metadata but names no native witness
for case, Unicode or firmlink routes through the canonical-path call. Only the
controlled adapter covers them, yet the call's real behaviour is the open
question.

Smallest coherent correction: name one canonicalization for `resolvedPath`,
policy targets, frame paths and bundle paths, or state which spelling each uses
and how dedup compares them. Add native VM witnesses for firmlink-alias roots
and for case- and Unicode-variant link targets.

### D7 — The anchor account omits exclusion witnesses and has no affected root (low)

spec:568 charges "fixed canonical region/mount witnesses"; spec:813-815 sizes
them at "at most twelve" 8,192-byte occurrences. The spec also requires retained
canonical paths and identities for exclusions:

- the four protected scopes (spec:246-249), compared by component and identity
  (spec:266);
- the known home cloud routes, Dropbox and OneDrive (spec:253-255).

No account holds those. They are either uncharged retained values, which
spec:818-819 forbids, or anchors, whose 12-occurrence shape is not enumerated. Six
regions, the Preboot witness, four protected scopes and two cloud routes already
make 13 or more occurrences. spec:817-818 also stops "the affected root" on
overflow, but the account is per job and is filled before any root turn.

Smallest coherent correction: enumerate the anchor and exclusion witness set and
size it. Define a job-level anchor failure, for example every root
INSPECTION_FAILED without progress.
