## Findings

Producer `8117c5dc7614` (application-localized-metadata-k212). Severity orders the
list. Measurements are from macOS 26.6.2 (25G83) as described in the log above.

### R1 — One ordinary app's large Info.plist fails the whole application catalogue (high)

- **Contract.** "Each fixed regular file is limited to 65,536 bytes" (spec:482-483);
  "Raw entry, file/key, call, copy or deadline exhaustion is population-wide
  FAILED/null" (spec:503-504); G11 gives "file bytes 65,536 … global FAILED/null
  precedence" (acceptance:100); `metadataFileBytes` 65,536
  (application-population.json:14). spec:442-443 separately treats an oversized
  preferred file as stopping only that episode, so the two readings disagree.
- **Evidence.** `/Applications/The Unarchiver.app/Contents/Info.plist` is 83,346
  bytes, and the bundle is returned by the fixed indexed application predicate.
  Apps declaring many document types sit close to the cap: OmniGraffle 63,038 and
  Microsoft Excel 60,279 bytes. The former Bundle route had no such cap; k212
  introduced it with the two fixed 64 KiB buffers.
- **Failure.** Under the global rule every application read on this Mac publishes
  FAILED with null items — the twelve launchers, Safari and Finder included —
  because of one unrelated app. Under the per-episode reading The Unarchiver
  publishes with null name, identifier and flags, so installationState is UNKNOWN
  and constrained launch is unavailable: a useful-choice loss the design does not
  accept.
- **Consequence.** k7 would implement a catalogue that a common third-party app
  breaks, and G10/V11 failures on ordinary hosts would reach k93 as native gaps
  although the cause is a design constant. Size the per-file bound from measured
  real information/name files, decide explicitly whether an oversized file is an
  individual metadata refusal or a population gate, and reconcile spec, G11 and
  the certificate together.

### R2 — The shipped system baseline alone breaks the certificate's input and inventory dimensions, so P1024 fails by construction (high)

- **Contract.** The 8,340,416-byte certificate adds "<=1,000,000 gross fixed-file
  input bytes and 64L records plus two <=32-byte locale components" with L = 4,096
  for the whole 2,048-spelling subject (spec:1018-1021, 517-523;
  application-population.json:62-66). Reads are charged per read even with buffer
  reuse (sources:339-340), and L includes unselected inventory names (spec:514-515).
  P1024 keeps "its existing baseline apps in the same measurement" (acceptance:319),
  and "Exceeding a finite assumption or production gate fails the useful subject"
  (acceptance:370-371).
- **Evidence.** The 325 indexed bundles under /System — the shipped baseline,
  before any third-party or fixture app — hold 943,084 bytes of selected Info.plist
  (median 1,797 per bundle) and 207 bytes of planned InfoPlist.strings: 943,291
  input bytes. Their direct .lproj inventory is 10,875 names (median 41 per
  bundle). The baseline therefore uses 94% of the subject-wide input dimension and
  2.7× the inventory dimension before P1024's 1,394 controlled bundles. Adding this
  Mac's 352 /Applications and /Library bundles gives 2,417,215 input bytes and 13,767
  inventory names.
- **Failure.** Re-deriving the certificate with the measured baseline alone gives
  6,816,128 + 943,291 + 10,875×128 = 9,151,419 bytes, above the 8,388,608-byte
  owned-copy gate, and that gate is population-fatal (spec:228-232, 503-504). The
  certificate does not certify its own required subject, and the acceptance text
  already makes that a failing outcome. The design asked for measurement
  (spec:521-528) but fixed dimensions the shipped OS refutes.
- **Consequence.** As designed, P1024/V11 cannot pass, and the likely runtime
  outcome on a populous Mac is whole-catalogue FAILED/null. spec:528 and k93's new
  duty (protected-home-search-k93, "Approved explicit metadata-reader gap duty")
  would bring this to Antony after implementation as a native coverage decision
  although it is measurable now —
  the shape of k210/R1. Re-derive the input and inventory dimensions from measured
  baseline plus the P1024 manifest, and revisit what is charged: cumulative gross
  charging of buffer-reused reads and owned copies of every unselected inventory
  name are the terms that scale with the baseline. The raw directory-entry gate
  held: E measured 14,805 (baseline) and 28,680 (this Mac's non-home bundles), under
  65,536.

### R3 — The closed name-file set misses InfoPlist.loctable, which most shipped apps use, and silently publishes unlocalized names (high)

- **Contract.** The reader probes only InfoPlist-macos.strings and InfoPlist.strings
  and calls these "the complete macOS file families" (spec:440-444;
  application-localized-admission.json:72; pinned at Taskfile.yml:630). When they
  are checked absent the plan falls through to "the information file's
  display/name" (spec:469-470). "No unlocalized Info.plist value … replaces a
  required known localized name" (sources:243-244), and review and G11/N8/V13 "must
  preserve useful localized names" (docs/requirements/modaliser-workflows.md:137).
- **Evidence.** 248 of the 325 shipped /System bundles carry their localized
  Info.plist keys in one `Contents/Resources/InfoPlist.loctable`, a binary plist
  keyed by locale; only 2 have any InfoPlist.strings. Even in English, 26 localized
  names differ from the plain Info name — FindMy → "Find My", VoiceMemos → "Voice
  Memos", NotificationCenter → "Notification Center", UniversalControl →
  "Universal Control"; Spotlight's display names confirm "Find My.app" and "Voice
  Memos.app". In German 141 differ (System Settings → "Systemeinstellungen").
  "loctable" appears nowhere in docs/, .grove/ or Taskfile.yml (the same search
  finds InfoPlist-macos.strings, and a mutated pattern finds nothing).
- **Failure.** For these apps every planned .strings is checked absent, so the
  reader publishes "FindMy", "VoiceMemos" and so on as BUNDLE_RESOURCE names with no
  diagnostic — the substitution the contract forbids — and non-English users get
  English names for most Apple apps. The former Bundle route would have read the
  loctable.
- **Consequence.** Acceptance cannot see it: L1500's localized controls are
  en.lproj/InfoPlist.strings fixtures (acceptance:195), P1024's English witnesses
  (Mail, Notes, Finder, Safari) coincide with plain names in English, and the design
  check pins the defective list. Admit the loctable format — locale selection over
  its keys rather than the .lproj inventory — or record its exclusion with Antony.
  Its sizes interact with R1 and R2: median 5,090 bytes, maximum 103,197, ten above
  65,536.

### R4 — With no matching preference the CF selector returns the first array element, so byte order picks the language ahead of the development region (low)

- **Contract.** The selector receives a byte-sorted array and explicit preferences;
  "no native directory order chooses a winner" (spec:462), and its results precede
  Base and the development region (spec:464-466; sources:256-257).
- **Evidence.** CFBundleCopyLocalizationsForPreferences with preferences
  [en-AU, en]: [ar, de, fr, ja] → [ar]; [ja, fr, de, ar] → [ja]; [de, fr] with
  [en-AU] → [de]. With no preference or English match it returns element 0.
- **Failure.** For an app without en/English/Base whose development region is,
  say, "it", an English user gets the byte-first locale's name rather than the
  development region's. Neither the spec nor G11 (acceptance:93-97) states or tests
  this case.
- **Consequence.** Rare, but a wrong-language user-facing name. State the backstop
  and either order the development region before positional backstop results or
  accept it with a control.

### R5 — The "closed" manifest leaves two construction choices open (low)

- spec:440 probes information files "in the selected information base", a term
  never defined; the manifest lists resource bases only, while
  `completeReaderPathSetEstablished` is true (application-localized-admission.json:4),
  and the check constructs name-file candidates only. For the Resources layout,
  historical CF kept Info.plist under Resources/, so an implementer must guess.
- spec:468-469 ("first usable explicit display name wins, otherwise usable bundle
  name") does not say whether a later base's display name beats an earlier base's
  bundle name.
- **Consequence.** Two implementations can read different files or names while
  both claim the closed plan. Name each layout's information base and the cross-base
  precedence, and construct information-file candidates in the check.

### R6 — The new read reach is required in the disclosure but pinned by neither the disclosure ADR nor G9/V10 (low)

- spec:88-89 adds "fixed application information/name files and direct
  localization names" to the required workspace-read disclosure — the visible
  condition of Antony's contents/listing exception. The host-disclosure ADR
  (docs/adr/native-workspace-requires-disclosure-capable-host.md:7-8) was not
  updated, and G9 (acceptance:83) and V10 (acceptance:183) enumerate only the
  earlier clauses and controls.
- **Consequence.** A host serving the pre-k212 read text passes G9/V10. Add the
  clause to the ADR and a failing control that removes it.
