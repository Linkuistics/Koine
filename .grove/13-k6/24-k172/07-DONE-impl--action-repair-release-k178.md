# action-repair-release-k178

## Goal

Ship the behaviour as workspace release/schema **1.0.1** under `koine-desktop/1`:
the repair SDL's three appended descriptions, an unchanged action shape, error
kinds and enums, a catalogue and conformance profile that say so, and a served
schema digest that differs from 1.0.0 on the same host and printer.

## Done when

- The served schema is the repair SDL's verbatim, with the 1.0.1 manifest and
  schema versions and the catalogue entry sealed with the actual signed packaged
  outputs' values (the signing identifier read from the bundle, as
  `task check:provider-catalogue` does).
- A new bundled profile (workspace 1.0.1/schema 1.0.1, desktop 1.0.0, full
  candidate rows) is held to what the signed host serves, by type, field,
  argument, nullability, default, deprecation and description, with its digest
  against the digest served. Candidate versions are pinned separately from
  canonical SDL and digest equality, and the check is seen red against mutated
  copies. The retained 1.0.0 profile and SDL are untouched and still pass against
  the retained bundle.
- The contract-only client is regenerated from the served schema and its coverage,
  and the findings record are reconciled with this contract; its documented-contract
  check (`task client`, `task conformance`) passes.
- `docs/specs/workspace-launch-and-open.md` and the workflow trace say what is
  now served.

## Notes

- A numeric served digest cannot be written before the actual composition exists;
  take it from the served schema and compare, never from a hand edit.

## Decisions (running log)

- **The shipped files are the repair SDL's body verbatim, and the retained 1.0.0 files are untouched.** `Providers/WorkspaceProvider/schema.graphql`
  is its own three-line header plus everything after the repair SDL's header (checked equal by `diff`); the repair SDL's header comment
  now says "as served" instead of "designed; unimplemented" (comments are not part of the printed schema, and the retained
  1.0.0 file keeps its own header). Manifest and `App/ProviderCatalogue.json` say 1.0.1 / 1.0.1; the signing identifier is unchanged.
- **The 1.0.1 profile is a new composed design file and a new profile, beside the retained pair.** `docs/design/desktop-workspace-repair-schema-extension-host.graphql`
  is the retained composition with exactly the three description lines replaced (generated by pairing the two SDLs' lines, not by hand), and
  `docs/design/profiles/core-desktop-workspace-repair-extension-host.json` pins desktop 1.0.0 and workspace 1.0.1/1.0.1 with the full candidate rows.
  `desktop-workspace-schema-extension-host.graphql`, `core-desktop-workspace-extension-host.json` and `workspace-schema.graphql` are not edited, because
  `scripts/verify-retained-workspace.sh` holds them byte-for-byte to the pinned revision.
- **Controls added for the repair**, in `scripts/conformance-lib.sh` and only for a profile pinning workspace schema 1.0.1: each of the three
  descriptions restored to the 1.0.0 text in turn, all three restored, and the retained release and the retained schema pinned for the repair.
  `scripts/vm-verify-conformance.sh` now holds the signed application to the new profile.
- **Tests**: the served-schema and verbatim-restriction tests follow the 1.0.1 design; new tests assert that the 1.0.1 bundle differs from the retained
  composition at exactly the three action coordinates, all as descriptions, with a different digest, and that the two profiles' pins refuse each other.
- **The client was regenerated from the capture of the conformance run itself**, copying `introspection.json` and the digest exactly as
  `task client:capture` does after its `conformance:vm` step, so no second VM run was spent; `task client` then passed. The older client
  findings records keep their own captures' digests (stated in the record), and the client README names the current and the retained one.
- **Digests**: retained 1.0.0 `3bab3a04…`, shipped 1.0.1 `0a489328…`, both the canonical digest of the composed design equal to the digest served.
- **Not done, left where the brief puts them**: the pairs, the per-user 1.0.1 variant and the selection fixtures (`action-repair-compat-k179`;
  the three update profiles still pin workspace 1.0.0 as the bundled row, so `task selection:*` and `task compat` were not run), and V.
- **No in-session review spent.** Every claim here is held by an executable check seen red first (the conformance controls, the catalogue
  self-test, the retained pin turning red on a 1.0.1 copy, the new tests); nothing rests on an unchecked judgement.
- **One unexplained first run.** The first `task test` of the session failed in `KoineServerTests` and I did not capture the log; the same tree
  then passed three times (426 tests). Recorded in `docs/verification/action-repair-release.md` as neither explained nor dismissed.
