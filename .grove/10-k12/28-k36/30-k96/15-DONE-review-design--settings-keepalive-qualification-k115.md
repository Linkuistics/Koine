### P2-2. The installable floor has two components and L1 measures one

The proposal defines F as the map size at the intermediary's install point and
derives the L1 limits from it (proposal :101-105, :109). L3 installs that
limit before exec of two no-op images (proposal :111). In the pinned source,
exec creates a new map and calls the size setter on it without checking the
result (kern_exec.c :1531-1532). The setter rejects a limit below that map's
size (vm_map.c :22094-22099).

So exec silently drops a limit that is above the
intermediary's F but below the producer image's map size. The usable floor is
the larger of the intermediary's F and the producer image's own exec-time map
size. The second is a property of the real producer image, its loader and its
linked libraries. Two no-op images cannot measure it (proposal :111).

The proposal also names no observation for F. It says what cannot supply F
(proposal :104) and requires a relation to the setter's accounting (proposal
:102-103). In the pinned source, `task_info` with `TASK_VM_INFO` reports
`virtual_size` as the adjusted map size (task.c :6035). That equals `map->size`
for an ordinary map (vm_map.c :1849-1864). The proposal could name that
relation, with its correspondence caveat.

Consequence: the installable map floor the k111 charter requires (k111 Done
when, first item) is understated. L1 and L3 can pass and leave the real
producer launch without an effective limit, and the design would not know. A
manifest cannot freeze L1 without an observation method.

Smallest correction: state the two components. Add a required measurement of
the producer image's exec-time map size on the actual producer subject, not a
no-op image. Name the candidate observation and its correspondence requirement.

### P2-3. L2's decisive evidence cannot separate route denial from incidental growth

L2 installs F plus eight pages, then requests at most nine pages through three
routes, and treats denial as qualifying the route (proposal :110). The headroom
is eight pages. The pinned mapping path compares the whole map size with the
limit (vm_map.c :3683-3684).

Any mapping the C runtime makes between the limit
call and the request consumes headroom. Examples are the allocator's first
arena, a stdio buffer, Mach port table growth and the report write. L1
brackets perturbation (proposal :109). L2 and L3 do not.

Consequence: a denial can come from exhausted headroom rather than from the
route's check. A "qualified" route can be a false positive. The remap route
the survey flags (survey :137-144) is exactly the case where this matters.

Smallest correction: sample the map size immediately before each request and
record it. Treat a case with consumed headroom as unresolved, not qualified.
Alternatively make each probe pre-touch its runtime before the limit call.
Then request a size that exceeds the limit by more than any observed incidental growth.

### P2-4. The raw rows gate on a bound the design cannot establish

The R rows require Q before any native row is admitted (proposal :216-218). Q
must come from corresponding kernel source (proposal :191-197). The survey
records that no corresponding source for the installed kernel was found
(survey :58). The proposal names no finite host observation that could bound
Q for the named cases.

In the pinned source, a pipe buffer grows through fixed steps up to four
times `PIPE_SIZE`, that is 64 KiB (pipe.h :73-81, sys_pipe.c :307). Growth is
conditional on a kernel-global kva budget (sys_pipe.c :957-959). Direct
transfer is compiled conditionally (pipe.h :115-125). So even on the pinned
kernel, Q depends on a global condition the study cannot control.

Consequence: as written, no R row can run on this host, and k112 must treat
raw capture as unqualified. The proposal does not say so. It presents 17
runnable cases.

Smallest correction: state plainly that the R group is blocked until source
correspondence exists, or add one finite probe. The probe writes with
`O_NONBLOCK` into a pipe whose reader is stopped, up to a declared ceiling such
as 256 KiB. It records the byte count at `EAGAIN` for the exact write pattern.
State that it qualifies that pattern on that host and boot under one kva state
only. Derive Q for the R rows from it with a declared margin.

### P2-6. The collector is a subject and a seam the proposal does not pin

The collector is a separate owned child (proposal :79) whose runtime, stack and
allocator contribution must be qualified (proposal :176-178). The subject table
pins the intermediary's language, flags and linkage (proposal :39). It has no
row for the collector. R3 holds "the collector at its approved barrier"
(proposal :212). The approval covers barriers in audited copies of the owner,
backend and caller modules (contract :205-210 and spec :510-513). A collector that
is not the backend module is outside that approval.

The proposal gives one reason for a separate process: survival across producer
exit (proposal :79). A reader thread in the backend also survives producer
exit. The stronger reason is unstated: a small image has a qualifiable runtime
contribution where the Python backend's does not. Without it the deletion test
is open.

Consequence: an unpinned subject sits in the six-process ceiling (proposal
:344-345). A barrier in it silently broadens the approval that k114 preserved.

Smallest correction: add a collector row to the subject table. Say whether the
collector is the backend module, a copy of it or a new image. If it is new,
state the ownership argument. Then present the barrier to Antony as a new
enabling point, or move the barrier to the backend copy.
